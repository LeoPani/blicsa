## 3. A combinação com o Zenodo (item 22)

O prompt observa, com razão, que a release precisaria ser recriada de qualquer forma para o
Zenodo capturar o depósito, e que por isso as duas operações se combinam sem custo adicional.

**Isso continua verdadeiro, mas o custo adicional deixou de ser zero:** recriar a release é
barato; reescrever 133 hashes e invalidar as referências dos relatórios não é. As duas
operações se combinam bem quando a reescrita é necessária. Ela não é.

**A ordem crítica permanece a mesma**, com ou sem reescrita:

```
limpeza de código → [reescrita de histórico] → force-push → ativar Zenodo → recriar release v2.0.0 → DOI
```

Reescrever histórico **depois** do DOI invalidaria o DOI. Se a reescrita for descartada, a
sequência vira: limpeza → ativar Zenodo → recriar release → DOI.

## 4. Recomendação

**Não reescrever o histórico.** Fundamento:

1. **Não há o que remover.** Zero assinaturas em 133 commits, verificado em doze padrões,
   incluindo os dois formatos de `Co-Authored-By` e o endereço de bot.
2. **O custo não é zero.** 133 hashes novos, tag e release recriadas, force-push, clones de
   terceiros quebrados, e todos os hashes citados nos relatórios de auditoria apontando para
   commits que deixaram de existir.
3. **O risco é assimétrico.** Reescrever sem necessidade pode quebrar coisas; não reescrever
   não deixa nada por resolver — porque não há nada.

Se a decisão for reescrever mesmo assim (por exemplo, para unificar os dois e-mails de autor
num só, que é um objetivo legítimo e **diferente** do que a Fase 4 previa), então:

- o backup do §1 vira pré-requisito;
- os relatórios em `docs/` precisam ter os hashes atualizados **depois** da reescrita;
- vale fazer numa passagem só, junto com qualquer outra correção de histórico desejada.
